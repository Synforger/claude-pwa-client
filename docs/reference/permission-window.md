# 承認の窓を画面へ出す

Claude Code は、道具を使う前に「この命令を実行してよいか」を端末の窓で訊くことがあります (承認の窓)。窓は端末にしか
出ないので、画面でチャットだけを見ていると、窓が開いたまま止まっていることに気づけません。この機能は、窓が開いた
ことを画面と通知で知らせ、画面のボタンや発話で答えられるようにします。

窓は Claude Code 自身のままです。client は窓を作り替えず、閉じもしません。端末で直に答えても、画面で答えても、
同じ窓に同じ答えが届きます。

## 設定

Claude Code の hook に `PermissionRequest` を足し、窓が開く直前の入力を client へ送ります。ほかの hook
([path-a-chat.md](../setup/path-a-chat.md#pwa-連携の-hook-を設定する-チャット表示に必須)) と同じ形で、port は backend に合わせます。

```json
{
  "hooks": {
    "PermissionRequest": [
      { "hooks": [ { "type": "command", "command": "curl -s -o /dev/null -m 2 -X POST http://127.0.0.1:8765/hooks/event -H 'Content-Type: application/json' -H \"X-PWA-SID: ${PWA_SID:-}\" -d @-" } ] }
    ]
  }
}
```

この hook は何も返しません (`-o /dev/null`)。許可も拒否も決めないので、窓はそのまま開き、答えを待ちます。
hook が運ぶのは、窓が訊いている入力の全文です。窓が開いているかどうかの根拠にも、通知の合図にもしません
(下の「窓があるかを決める」)。窓を出さずに断る hook がほかにあると、hook が呼ばれても窓が出ないことがあるためです。
`X-PWA-SID` のタブの id が、その会話を結んでいるタブと違う hook は受けません。

`AskUserQuestion` と `ExitPlanMode` にも同じ hook が呼ばれますが、client はこの 2 つを窓として画面に出さず、
今までどおり問いと計画の承認の画面で扱います。この 2 つの hook は、会話の記録にまだ呼び出しが書かれていない間
(問いは答えるまで書かれない版があります) の窓の種類を知るために使います。

hook を足していないタブでも、窓は画面に出ます。ただし入力の全文は出せず、記録にある入力を見せ、キーでは答えられません
(端末で答えます)。`Notification` の通知は今までどおり届きます。

## 窓があるかを決める

**窓があるかは端末の画面で決め、何の窓かは会話の記録で決めます。**

- 入力欄: 画面の最後の罫線 2 本の枠で、上の罫線の直下の行が `❯` か `>` で始まり (打ちかけの文が `1.` で始まっても入力欄です)、
  枠の下に選択肢の足元の文 (`Esc to cancel`・`Esc to exit`・`Enter to select`・`Enter to confirm`) も、印のついた選択肢も無い画面です。
  上の罫線にはタブの名前などの題が入っていてもかまいません
- 窓: 入力欄ではなく、印 (`❯`) のついた番号の選択肢がある画面です。左右に枠の線がついていても、線を外して読みます。
  返事の本文に `1. Yes` / `2. No` が書いてあるだけで、入力欄が下に出ている画面は窓ではありません
- 種類: 会話の記録の、結果がまだ出ていない道具の呼び出しの一番古い 1 本で決めます。`AskUserQuestion` は問い、
  `ExitPlanMode` は計画の承認、ほかの道具は承認です。記録に呼び出しが無い間は、答えが出ていない問い・計画の hook の道具で
  決めます。どちらも無い窓 (`/model` の選びなど) は、どれでもありません。記録の今のやり取りの区切りは、人の発話と
  中断の印だけです (道具が読み込んだ内容などの行や、サブエージェントの行では切りません)
- 窓が 2 つ続く時は、記録の呼び出しの順に 1 つずつ画面に出ます。`pending_permission` もいつも一番古い 1 つです

画面の見張りは、タブごとに繰り返す見回りが 1 回の読みで済ませます。入力欄が 2 回続けて見えたら、client が覚えている窓を
忘れます。道具の結果が記録に書かれた時、答えのキーを打った時、会話が終わった時、新しい会話が始まった時、タブを再起動した
時、タブの端末が無くなった時にも消えます。backend を再起動した後は、記録の今のやり取りの分を別の thread で読み直して
種類を決めます。

## 画面が見るもの

承認の窓が開いているタブの状態 (`agent_status.pending_permission`) は、窓が無ければ `null`、開いていれば次の形です。

| 欄 | 中身 |
|---|---|
| `number` | 窓ごとに増える番号。答える時に窓を指す |
| `tool_use_id` | 会話の記録の道具の呼び出しの id。まだ結べていない間は `null` |
| `tool_name` | 道具の名前 (`Bash` など) |
| `input` | 窓が訊いている入力の全文。実際に走るのはこちら。hook が来ていない窓では記録の入力 |
| `record_input` | 会話の記録にある入力。`input` と同じなら `null`。違う時は、hook が入力を書き換えている |
| `answerable` | キーで答えてよい窓か。次の 3 つが全部真の時だけ真 |
| `index` / `count` | 1 回の応答で窓が続けて開く時の「k / N」 |
| `opened_at` | 窓が開いた時刻 (epoch 秒) |

`answerable` が真になる条件は、次のとおりです。

1. 印のついた行を含む選択肢の塊が、ラベルを削らずに `Yes` と `No` の 2 行だけ (「Yes, and always allow」「Yes (always allow)」
   や 3 つ目の選択肢がある窓は、端末で答えます。Escape は打ちません)。画面の上の方にある前の返事の番号の並びは数えません
2. 題が `Bash command` の窓で、題より深く字下げされた命令の欄の全部が、hook の入力の `command` (あれば `description` も) と空白を除いて
   等しい。含むだけでは足りません。理由の文は数えません。欄を読めない窓や、命令が途中までしか見えない窓は答えません
3. その窓を、直前の答えの後に画面で見た (1 つ答えたら、次の窓は画面が描き替わるまで答えません)

窓が開いていることは、画面の上部のボタン、タブの一覧の印、通知で知らせます。通知は窓 1 つにつき 1 本で、画面が窓を初めて
見せた時に送り、文は道具の名前だけです (入力は載せません)。

## 答える

```
POST /pty/{id}/permission/answer
{"number": 3, "answer": "allow"}      // または "deny"
```

| 返事 | 意味 |
|---|---|
| `{"ok": true}` | 答えのキーを 1 つ打った |
| `{"ok": false, "reason": "closed"}` | そのタブの画面に承認の窓が出ていない。何も打っていない |
| `{"ok": false, "reason": "mismatch"}` | 窓はあるが、キーで答えてよい形ではない (上の 3 つのどれかが偽)。何も打っていない。端末で答える |
| `{"ok": false, "reason": "not_typed"}` | tmux がキーを受け取らなかった |
| 409 `permission_stale` | `number` が今の窓ではない (古い窓への答え)。何も打っていない |

画面を読み直すのと打つのと「答えた」印を付けるのを、そのタブへの打鍵の順番の中で 1 つの手として行うので、読んだ後に画面が
変わることも、同時に来た 2 つの答えが 2 回打たれることもありません。
打つキーは、画面の選択肢から読みます。ラベルが `Yes` の行が「許す」、`No` の行が「断る」です。Enter は打ちません。
答えのキーを打ったら、窓はすぐに閉じた扱いにします。

答えの口は `/pty/` の下の、人の口 (画面とアプリ) です。`/ws/pty/` の端末も人の手です。

### 答えの語

人が打った発話の全文が次の語だけの時、承認の窓が上の条件で答えられる形で出ていれば、発話ではなく窓への答えになります。
吹き出しは作らず、「窓に答えました」を返します。前後の空白と句読点は無視します。声で聞き取った発話の頭の印 (`[voice]`) は
外して判定します。

| 語 | 答え |
|---|---|
| 許可 | 許す |
| いいえ・だめ・拒否 | 断る |

「はい」は答えに数えません。エージェントがチャットで訊いた問いへの「はい」と区別できないためです。答えの語を数えるのは
人の口 (`/pty/{id}/send`) だけで、別のタブの連絡や client 自身の送りには効きません。窓が答えられる形でない時の語は、
答えにせず、ほかの発話と同じに扱います (下の「窓の間に打った本文」)。

### 問いと計画の承認への答え

問い (`AskUserQuestion`) と計画の承認の窓への人の答えは、`/pty/{id}/send` の本文に `"answers_choice": true` を付けて
送ります。人の口だけが読み、声の印は付けません。記録と画面の両方が問いか計画の窓の時だけ打ちます。承認の窓や、窓が
無い時は `{"ok": false, "reason": "window_open"}` を返し、数字を発話として打つことはしません。入力待ちのチップ
(`/pty/{id}/send-raw-key`) と、Enter 無しの 1 文字の送り、本文の無い Enter、Escape と `C-c` 以外の key の送りも同じ扱いで、
承認の窓の間は断ります (Escape と `C-c` は人が止める手なので通します)。

## 窓の間に打った本文は預かる

端末に本文を打つと、その Enter は窓の最初の選択肢 (`1. Yes`) を確定します。本文の 1 文字が選択肢になることもあります。
窓の間に別のタブの連絡を打つと、窓が許可で閉じ、命令が走り、連絡は会話のどこにも残りません。

そこで、本文を打つ手の中で画面を 2 回読みます。入力欄を消す前と、Enter の直前です。窓が出ていたら、1 文字も打ちません。
待っている間に窓が開いても、同じです。打ちかけの文が `1.` で始まっていても、入力欄は入力欄です。添付つきの送りも、
届いたかの確かめの打ち直しも同じ道を通ります。

窓が出ていた時の扱いは、呼び手が決めます。

| 呼び手 | 窓の間 | 返事 |
|---|---|---|
| 人の発話 (画面・声・アプリ)、別のタブの連絡 | 預かり、窓が閉じたら届ける | `{"ok": true, "held": "window"}` |
| client 自身の送り (自動の入れ替え・口座の移し・知らせ・子の最初の発話・`tabs ask`) | 預からず断る。頼んだことに数えない | `{"ok": false, "reason": "window_open"}` |
| 記録に呼び出しの無い窓 (`/model` の選びなど) への本文 | 預からず断る | `{"ok": false, "reason": "window_open"}` |

- 別のタブの連絡 ([agent-messages.md](agent-messages.md)) は、起こした直後のタブへの連絡も、送り主に `預かりました` と返します
  (`届きました` とは言いません)
- 画面から送った本文は、窓が閉じるまで届きません。画面の吹き出しは「預かり中」になります
- 人の Escape と、問いの番号のような 1 つのキーは預かりません。声の割り込みは、窓が出ている間は Escape を打ちません
- 送った本文の確認 ([agent-messages.md](agent-messages.md#claude-が動いていないタブへ送った時)) は、窓の間は Enter を打ち直しません

### 預かった本文を放す

預かった本文は、会話の id とともに状態の置き場の `window_hold.json` (自分だけが読める) に書き、backend を再起動しても残ります。
放すのは、画面が入力欄を 2 回続けて見せた時です。答えた直後には放しません。次の窓がすぐに出ることがあるためです。
タブごとの見回りが毎回見るので、client が窓を覚えていなくても放せます。放す時は来た順に打ち、放している途中でまた窓が出たら、
残りはその窓が閉じるまで待ちます。

次の時は、打たずに捨てて、送り主に届かなかったと知らせます。file の一部が読めない時は、読めない件だけを捨てて起動します。

- 会話が替わった (再起動・入れ替え・口座の移し・`/clear`) 後は、前の会話あての本文を新しい会話へ打ちません
- タブが閉じた、またはタブの端末に Claude が居ない

知らせ方は、画面から送った本文なら吹き出しが「届かなかった」になって本文が入力欄へ戻り、別のタブの連絡なら送り主のタブへ
client から 1 行の知らせ (`<message-not-delivered>`) が届きます。眠っている送り主は起こしません。

## 窓が開いているタブの扱い

窓の答えは人にしか出せないので、承認の窓が開いているタブは次のように扱います (判定の理由は `permission_open`)。

| 仕組み | 扱い |
|---|---|
| [眠り](sleep.md) | 眠らせない |
| [自動の入れ替え](rollover.md) | 締めを頼まない。入れ替えの途中の数にも入れない |
| [口座の振り分け](account-fallback.md)・[止める線](account-hold.md) | 区切りと見なさず、移さず、止めず、区切りを頼む連絡も送らない |
| [子のタブの見回り](child-sessions.md#止まった子の見回り) | 窓が 5 分続いた子を、親に 1 回知らせる |

## 困った時

| 症状 | 見る所 |
|---|---|
| 窓の入力が全文で出ない・`answerable` が偽 | `PermissionRequest` の hook を足したか。タブを起動し直した後か (hook は起動時に読まれる)。窓が 3 択ではないか |
| 画面で答えても `closed` が返る | 端末に承認の窓が出ていない。窓が出てから答える |
| 画面で答えても `mismatch` が返る | 窓が `Yes` / `No` だけでない、または命令が画面で途中までしか見えない。端末で答える |
| 預かった本文が届かない | 窓・計画の承認・問いが残っていないか。画面が入力欄を 2 回続けて見せると届く |
| 預かった本文が「届かなかった」になった | 会話が替わった、またはタブに Claude が居ない。送り直す |
